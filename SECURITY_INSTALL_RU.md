# LTL Secure V3 — пошаговая установка и защита

## Что исправлено

1. **Защита от подмены роли в браузере**
   - Сервер больше не доверяет `localStorage` с ролью `admin/head`.
   - Полное состояние (`nexus_get_state`) выдаётся только после серверной проверки роли.
   - Роль привязана к `auth.uid()` через `authUserId`, а не к редактируемому username из Auth metadata.

2. **Убрана опасная выдача полного состояния обычным пользователям**
   - `nexus_get_state` теперь только для staff.
   - Публичный клиент получает `nexus_get_public_state`, где исключены `nexus_users` и `nexus_support_messages`.

3. **Прямой доступ к таблице закрыт**
   - `anon` и `authenticated` не получают SELECT/INSERT/UPDATE/DELETE на `public.nexus_users`.
   - Изменения идут только через защищённые RPC.

4. **Защищён профиль**
   - Обычный пользователь может менять только avatar/avatar_url.
   - Нельзя через RPC повысить роль, заменить email, `authUserId` или `teamId`.

5. **Исправлена конфигурация Supabase**
   - V3 действительно использует `supabase-config.js`, который уже лежит рядом с сайтом.

6. **Убран старый прямой браузерный доступ к `ltl_state`**
   - Старый reset-код больше не обращается к таблице напрямую.

7. **Storage**
   - Добавлены политики загрузки/изменения/удаления только для авторизованных пользователей.
   - Публичное чтение остаётся возможным для текущих public URL картинок.

## Важное ограничение про DDoS

Файлом сайта невозможно полностью защитить сервер от DDoS. DDoS нужно останавливать **до Vercel/Supabase** через CDN/WAF.

Рекомендуемая схема:

`Пользователь → Cloudflare DNS/Proxy → Vercel → Supabase`

Cloudflare должен быть включён как Proxy для домена. Не публикуй прямые origin-адреса/служебные IP.

## Шаг 1. Сделай резервную копию

- [ ] Сохрани текущую базу Supabase.
- [ ] Не удаляй `ltl_state`, пока V3 не проверена.
- [ ] Сохрани текущий проект Vercel/GitHub.

## Шаг 2. Установи SQL

1. Открой Supabase.
2. Выбери проект.
3. Открой SQL Editor.
4. Создай новый запрос.
5. Сначала убедись, что V2 уже установлена.
6. Запусти **`schema_v3_secure.sql`** целиком.
7. Если Supabase сообщает об отсутствующем `storage.objects`, значит Storage ещё не настроен — сначала создай bucket `ltl-media`.

## Шаг 3. Проверь Authentication

В Supabase → Authentication:

- [ ] Включи email confirmation, если он нужен проекту.
- [ ] Установи сильную политику паролей (рекомендуется 12+ символов).
- [ ] Включи CAPTCHA/anti-bot защиту, если она доступна для твоего тарифа.
- [ ] Проверь rate limits для Auth/API.

### Важно про текущую регистрацию

V3 ограничивает `nexus_create_profile` так, что профиль можно создать только для текущего `auth.uid()`.

Если в проекте включено подтверждение email и после `signUp()` сессия не создаётся, текущая форма регистрации должна быть переделана на серверный trigger/Edge Function. Не отключай подтверждение email только ради обхода этой проверки.

## Шаг 4. Storage

В Supabase → Storage:

- [ ] Проверь bucket `ltl-media`.
- [ ] Не разрешай anonymous INSERT/UPDATE/DELETE.
- [ ] Примени политики из `schema_v3_secure.sql`.
- [ ] Проверь максимальный размер файла.
- [ ] Для логотипов/аватаров желательно разрешить только image MIME types.
- [ ] Ограничь размер изображения примерно 2–5 MB.

Если bucket должен быть приватным, нужно отдельно переделать frontend на signed URLs. Сейчас старый frontend использует public URL.

## Шаг 5. Vercel

Загрузи папку `ltl_v2_build` как новый deploy.

В репозитории должны быть:

- `index.html`
- `supabase-config.js`
- `schema_v3_secure.sql`
- `vercel.json`
- `.gitignore`
- `.env.example`

**Никогда не добавляй `service_role` key в `index.html`, GitHub или Vercel frontend variables.**

Publishable/anon key может находиться в браузере. Секретом является `service_role`.

## Шаг 6. Cloudflare против DDoS

Для домена:

1. Добавь домен в Cloudflare.
2. Перенеси DNS на nameservers Cloudflare.
3. Включи Proxy для веб-записей домена.
4. SSL/TLS → поставь **Full (strict)**.
5. Security → WAF.
6. Включи Managed Rules.
7. Включи Bot protection/антибот, если доступно.
8. Создай rate-limit правила.

Рекомендуемые правила:

### Авторизация

Ограничить:

- `/auth/*` если используется отдельный backend;
- запросы к Supabase Auth/API;
- частые POST-запросы.

Пример логики:

`IP → больше 10 попыток входа за 1 минуту → временный challenge/block`

Не ставь слишком маленький лимит, иначе можно заблокировать обычных пользователей за мобильный NAT.

### Общий сайт

Для обычных GET:

`IP → несколько сотен запросов/мин → challenge`

Для POST/RPC:

`IP → десятки запросов/мин → challenge/block`

Точные значения лучше подобрать по реальному трафику.

## Шаг 7. Защити Supabase

В Supabase:

- [ ] Не публикуй `service_role`.
- [ ] Не давай frontend доступ к таблицам напрямую.
- [ ] Проверяй RLS на каждой новой таблице.
- [ ] Для каждой `SECURITY DEFINER` функции проверяй `auth.uid()`.
- [ ] Не возвращай email/password/private messages публичным RPC.
- [ ] Не храни пароли в `nexus_users`.
- [ ] Включи MFA для владельца/администраторов Supabase.
- [ ] Ограничь доступ к панели Supabase.

## Шаг 8. Что проверить после установки

### Тест 1 — подмена admin

1. Войди обычным пользователем.
2. Открой DevTools → Console.
3. Измени локальную сессию/роль на `admin`.
4. Обнови страницу.
5. Серверные RPC `nexus_get_state` и `nexus_set_state` должны отказать.

Важно: UI можно подделать в браузере. Защищается именно серверная операция.

### Тест 2 — прямой SELECT

Обычный frontend пользователь не должен иметь возможности выполнить:

`select * from public.nexus_users`

через Supabase Data API.

Ожидаемый результат — permission denied/RLS denial.

### Тест 3 — support

Обычный пользователь не должен получать `nexus_support_messages` через public state.

### Тест 4 — профиль

Обычный пользователь не должен через RPC изменить:

- role
- email
- authUserId
- teamId

### Тест 5 — Storage

Anonymous пользователь не должен загружать/удалять файлы в `ltl-media`.

### Тест 6 — DDoS

Не запускай реальный DDoS-тест на production. Для проверки WAF используй безопасный тестовый rate-limit сценарий или staging-домен.

## Шаг 9. Защита от утечки данных

Запомни главное:

- Всё, что сайт показывает пользователю, нельзя считать секретом.
- Не отправляй пароли, service_role, приватные токены или секретные ключи в HTML/JS.
- Не возвращай лишние поля из RPC.
- Не клади приватные сообщения в публичный state.
- Не используй `localStorage` как источник авторизации.
- Сервер всегда должен проверять права самостоятельно.
